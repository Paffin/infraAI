# Симулятор отказов

Симулятор — часть детерминированного движка (`backend/crates/engine/src/sim.rs`). Для архитектуры и сценария отказа он считает установившееся
состояние **после всего автоматического восстановления**, время перерыва, окно потери данных (RPO), риск split-brain, остаточную ёмкость и
цепочку объяснений. LLM не участвует: результат воспроизводим, а каждая величина помнит, *задана она архитектором или принята по допущению*.

## Сценарии

| Сценарий | Что происходит | Данные |
|---|---|---|
| `none` | штатная работа (базовые нагрузки и ёмкость) | — |
| `instance {nodeId, count}` | теряются `count` экземпляров узла (под, ВМ) | сохраняются (сбой, не уничтожение) |
| `node {nodeId}` | падает весь узел | сохраняются |
| `unit {unit}` | падают все члены группы (кластера) | сохраняются |
| `zone {zoneId}` | площадка (ЦОД/AZ/облако/стойка) уничтожена | **теряются**, если нет реплики на живой площадке или бэкапа |
| `link {a, b}` | разрыв сети между двумя площадками; обе стороны живы | сохраняются |
| `sites {zoneIds}` | уничтожены несколько площадок сразу | теряются |
| `geo {geo}` | уничтожены все площадки гео-домена (город, район) | теряются |

Набор сценариев для проверок строится автоматически (каждая площадка, пары площадок, каналы, гео-домены, отказ каждого узла/экземпляра)
и ограничен настройкой `scenarios.maxCount` (400 по умолчанию) — комбинаторного взрыва нет. Сценарии вида «одна площадка» соответствуют
требованию «какой отказ нужно переживать» (`instance` / `site` / `geo`).

## Модель

* **Площадка** (`dc`, `cloud`, `az`) — единица отказа питания/сети и сетевого разделения. Узлы без зоны глобальны (пользователи,
  anycast DNS) и достают до всего.
* **Юнит** — узлы одной `group` (или одиночный узел). Поведение юнита определяет, когда он обслуживает: `stateless`,
  `primary_replica`, `consensus`, `quorum_log` (поведение берётся из каталога).
* **Связность попарная.** Нарисованные связи плюс неявная сетка между площадками, где живут члены одного юнита (`implicitMesh`). Разрыв
  одного канала не предполагает транзита через третью площадку, пока не включён `transitRouting`.
* Узел **работает**, если жив и у каждой его *жёсткой* зависимости есть обслуживающий член, до которого можно дотянуться. Мягкая
  зависимость (кэш, `hard: false`) даёт деградацию, но не остановку. Сервис жив, если обслуживаются точки входа.

### Поведения

| Поведение | Правило |
|---|---|
| `stateless` | обслуживает, пока жив хотя бы один экземпляр |
| `consensus` (etcd, Consul) | нужен кворум голосов (`votes`); без кворума юнит не обслуживает |
| `quorum_log` (Kafka, ClickHouse, OpenSearch) | запись возможна, пока доступно `minInsync` реплик |
| `primary_replica` (PostgreSQL, Redis, Vault) | см. ниже |

### Primary / replica

* Кандидат на повышение выбирается **по каждому кандидату отдельно**: есть ли у него синхронная/асинхронная связь с primary, достижим ли
  он, разрешено ли ему повышение (`failover`: `auto` / `manual` / `none`).
* **Автоматическое** переключение требует кворума арбитра (`dcs` — etcd/Consul — или witness). Без кворума автопереключение небезопасно:
  оно либо не происходит (`manual_failover`: оператор повышает вручную, время — `assumptions.manualFailoverSeconds`), либо создаёт
  **split-brain** — событие `split_brain` и красная метка в результате.
* **Fencing:** primary, потерявший кворум, останавливает запись (`fenced`) — два писателя не появляются.
* Синхронная реплика недоступна → по настройке связи (`onReplicaLoss`) запись блокируется (`writes_blocked`) или primary переходит на
  асинхронную запись (`async_fallback`, RPO > 0).
* Окно потери данных при переключении = лаг асинхронной репликации (`lagSeconds`, иначе `assumptions.asyncLagSeconds`); у синхронной — 0.
  Если у связи есть `mitigation` (например, outbox-паттерн для очередей), потеря не считается потерей бизнес-данных.

### Данные и восстановление

Если юнит утрачен вместе с площадкой:

1. есть живая реплика в другой площадке → данные сохранены (`replicated_elsewhere`), RPO = лаг;
2. иначе есть живое хранилище бэкапов → восстановление (`restore_from_backup`): RPO = интервал копирования
   (`intervalSeconds` связи / `backupIntervalSeconds` хранилища), время = `restoreSeconds`;
3. иначе данные **потеряны безвозвратно** (`data_lost`).

Потеря данных — не «нулевой RPO»: в цели RPO и в правиле `DR-RPO-01` она учитывается как нарушение (ключ находки `…:lost`).

### Время восстановления (RTO)

Складывается из шагов, лежащих **на пути запроса** (неблокирующие фоновые сервисы вроде Vault для RTO не считаются): время автопереключения
(`failoverSeconds` + выбор лидера `electionSeconds`), маршрутизация трафика (GSLB: `healthCheckSeconds × failThreshold + dnsTtlSeconds`),
масштабирование pilot-light (`failoverReplicas`, `scaleUpSeconds`), ручные шаги, восстановление из бэкапа. Результат — `recovery`:
`none` / `auto` / `manual` / `never` (без ремонта не восстановится).

### Ёмкость

Нагрузка (`rpsPeak`, умноженная на запас роста) распространяется вниз по зависимостям через `fanout`; ёмкость юнита — сумма
производительностей живых экземпляров (`rpsPerReplica` или `rpsPerVcpu × vCPU`). Результат — минимальное отношение «ёмкость / нагрузка»
по юнитам (`capacityRatio`) и узкое место; после потери площадки «холодный» кэш повышает долю запросов к базе (`fanoutColdCache`).
Цель — `minCapacityDuringFailure` (0.8 по умолчанию).

### Что видит пользователь

Результат (`SimResult`): состояние сервиса (`up` / `degraded` / `down`), восстановление, RPO (с пометкой «по допущениям»), список
потерянных данных и split-brain, ёмкость, состояние каждого узла и связи для подсветки на холсте и список событий — в порядке
причинно-следственной цепочки. На холсте: «Что если отказ» (узел, площадка, канал, две площадки, домен), матрица всех сценариев и
кнопка «Показать отказ» в карточке замечания, которая воспроизводит сценарий, вызвавший находку.

## Допущения

Всё, чего нет в схеме, берётся из `engine.assumptions` (редактируется в админ-панели): `asyncLagSeconds`, `manualFailoverSeconds`,
`restoreSeconds`, `backupIntervalSeconds`, `defaultFailoverSeconds`, `minCapacityDuringFailure`, `syncMaxRttMs`, `transitRouting`, … Значение,
взятое из допущения, помечается в интерфейсе («по допущениям», `~`) и снижает достоверность оценки: правило превращается в `нет данных`,
пока значение не подтверждено явно.
