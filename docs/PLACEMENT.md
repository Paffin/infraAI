# Размещение по площадкам

Мастер размещения собирает **полную схему** платформы для любого числа площадок — один ЦОД со стойками, два ЦОД с арбитром, пять, десять, двадцать, несколько регионов,
основная площадка с резервной. Он ничего не «доказывает»: результат проходит тот же движок проверок, что и схема, нарисованная руками, а замечания и «почему так»
показываются рядом. Принцип остаётся прежним — [генератор предлагает, движок проверяет, человек решает](ARCHITECTURE.md).

Открывается карточкой **«Мастер размещения»** в диалоге нового проекта (создаёт проект) и командой **«Разместить по площадкам…»** палитры команд редактора, `Ctrl/⌘+K`
(заменяет схему открытого проекта после подтверждения; `Ctrl+Z` возвращает прежнюю, а требования проекта — RPS, RTO, RPO, бюджет — становятся отправной точкой).

## Что выбирает пользователь

| Параметр | Что значит |
|---|---|
| **Схема размещения** (pattern) | один ЦОД, два ЦОД + арбитр, N площадок, несколько регионов, основная + резервная. Схема задаёт допустимые числа и умолчания |
| **Площадок** | рабочие ЦОД, зоны доступности или облачные регионы: от `minSites` до `maxSites` схемы |
| **Регионов** | на сколько гео-доменов делятся площадки (катастрофа региона уносит все его площадки). Только у схем, где регионы выбираются |
| **Стоек на площадку** | больше одной — стойка становится доменом отказа со своими сценариями (`HA-RACK-*`, `HA-QRM-03`) |
| **Площадок могут отказать одновременно** (`k`) | `авто` — сколько позволяет число площадок (большинство должно остаться), либо число; данные и кворум размещаются минимум на k+1 площадках |
| **Тип площадок** | `dc` / `az` / `cloud` (из типов зон каталога) |
| **Состав платформы** | какие слои включены; зависимые слои включаются сами (`needs`) |
| **Продукт и вариант** каждого слоя | любой продукт функции слоя и любой его вариант: PostgreSQL на Patroni или Amazon RDS, Kafka на KRaft или MSK, Redis Sentinel или Cluster… ([CATALOG.md](CATALOG.md)) |
| **Требования** | RPS, RTO, RPO, бюджет: пусто — берутся значения схемы |

В мастере сразу видны: **карта площадок** (роли «рабочая / резервная / арбитр / копии», регионы, стойки), **вердикт движка** (оценка, что переживает схема, стоимость в месяц,
замечания), **замечания генератора** (где он вынужден был отступить от просьбы) и **сравнение**: та же платформа при другом числе площадок или другой схеме — что дороже и что переживает.

## Схемы по умолчанию

| Схема | Площадок | Регионы | Стоек | Переживает | Особенности |
|---|---|---|---|---|---|
| `single-dc` — один ЦОД, несколько стоек | 1 | один | 2–6 (3) | отказ стойки (`rack`) | потеря ЦОДа = восстановление из внешней копии; для неё добавляется внешняя площадка резервных копий |
| `two-sites` — два ЦОД + арбитр | 2 | один | 1–4 | потеря площадки (`site`) | арбитр (witness) на третьей независимой точке; RPO = 0 за счёт синхронной реплики |
| `n-sites` — N площадок, кворум большинством | 3–20 (5) | один | 1–3 | `k` площадок сразу (`k` = авто, не больше `maxSiteFailures`) | нагрузка делится на N площадок, голоса кворума — на нечётном числе мест |
| `multi-region` — несколько регионов | 2–20 (4) | 2–6 | 1–3 | потеря региона (`geo`) | синхронная репликация внутри региона, асинхронная между регионами, кластер на регион |
| `active-standby` — основная + резервная | 2–8 (3) | 2 | 1–3 | потеря региона (`geo`) | резервная площадка держит «pilot light» и масштабируется при катастрофе (`standbySites`) |

Всё это — данные: схемы редактируются в **Администрирование → Размещение → Схемы размещения**, а свои добавляются кнопкой «Создать свой элемент».

## Как строится схема

1. **Топология.** Генератор создаёт площадки (и стойки) нужного типа, раскладывает их по регионам (`regions.mode`: `single` / `count` / `per_site`), добавляет **площадки-арбитры**,
   если рабочих площадок не хватает, чтобы после `k` потерь остался нечётный кворум, и **внешнюю площадку копий**, если схеме нужна резервная копия вне ЦОД.
   Связи между местами получают задержку, пропускную способность и лаг репликации по профилю: внутри площадки, внутри региона, между регионами.
2. **Слои платформы** (`stack`) размещаются по области (`scope`):
   * `global` — вне площадок (пользователи, DNS, CDN);
   * `site` — по одному узлу на место (площадку или стойку), размер считается из нагрузки (`sizing`: `load` — столько экземпляров, чтобы выдержать пик, или `fixed`);
   * `cluster` — один логический сервис, распределённый по местам по **поведению** продукта:

     | Поведение | Как размещается |
     |---|---|
     | `stateless` | экземпляры по местам |
     | `primary_replica` | primary на рабочей площадке, реплики на других площадках (`copies.min..max`), последняя — в резервной; арбитр или DCS, если продукт не управляемый и не имеет собственного кворума |
     | `consensus` | нечётное число голосов (`minVoters`…`maxVoters`, не менее 3) по независимым местам, лишние — арбитры |
     | `quorum_log` | брокеры/узлы по местам, фактор репликации и `minInsync` из свойств слоя |

   * `single` — один узел в одном месте (`place`: `first`, `last`, `witness`, `offsite`): GitOps на арбитре, хранилище копий вне площадки.
3. **Продукт слоя** берётся из каталога: по умолчанию `kind` слоя, но можно выбрать любой продукт той же **функции** (`function`) — не только перечисленные `alternatives`.
   **Вариант** меняет и размещение: управляемый сервис (`managed`) не требует DCS и арбитра и ставится как один логический узел провайдера; Vault на встроенном Raft размещается как
   кластер голосующих; Redis Sentinel — со «своим кворумом»; CloudNativePG — с кворумом платформы.
4. **Связи** строятся из `from` слоя: `same` (к ближайшему узлу), `all` (каждый с каждым), `each_target`; `unless` — запасной путь, если слой выключен (без WAF балансировщики
   получают трафик прямо от GSLB). Связи между площадками шифруются (`tlsBetweenSites`).
5. **Запасные места и отступления.** Если чего-то не хватает, генератор не молчит, а добавляет **замечание** (`notes`), которое мастер объясняет на языке пользователя:

   | Код | Что случилось |
   |---|---|
   | `witness_sites` | добавлены площадки-арбитры, чтобы у кворума всегда было большинство |
   | `site_failures_clamped` | отказов одновременно меньше запрошенного: при данном числе площадок больше не пережить |
   | `copies_limited`, `single_copy` | копий данных меньше, чем нужно (не хватает мест), или одна — потеря её площадки потеряет данные |
   | `no_authority` | негде разместить арбитра: автопереключение отключено, остаётся ручное |
   | `arbiters_share_locations`, `voters_share_locations` | не хватает независимых мест: часть голосов или арбитров делит место |
   | `cluster_per_domain` | кластер разбит по регионам, между ними асинхронная репликация |

6. **Проверка.** Готовая архитектура оценивается движком — оценка, цели RTO/RPO, сценарии «потеряли `k` площадок», «изолировали площадку», стойки, ёмкость, стоимость.
   Сгенерированная схема не получает поблажек: если она нарушает правило, вы видите это так же, как в рисованной.

> Покрытие проверяется тестом: **620 комбинаций** «продукт × вариант × число площадок (1, 2, 3, 5, 10)» генерируются и проверяются без критичных находок.
> Единственное известное исключение — продукты без собственной HA (например, Meilisearch): тест перечисляет их явно (`KNOWN_LIMITS`), а не прячет.

## Сценарии отказов для многих площадок

При трёх и более площадках одной «потери ссылки» недостаточно, поэтому набор сценариев расширяется ([SIMULATION.md](SIMULATION.md)):

| Сценарий | Смысл |
|---|---|
| `zone` (стойка, площадка) | зона уничтожена, данные в ней потеряны |
| `sites {zoneIds}` | несколько площадок сразу (все комбинации размера `k`, до `scenarios.maxCombinations`) |
| `isolate {zoneIds}` | группа площадок отрезана от остальных, но продолжает работать и видит друг друга (обрыв WAN, пиринг) |
| `link {a, b}` | разрыв канала между двумя площадками |
| `geo {geo}` | уничтожены все площадки региона |

Правила: `HA-SITE-02` (переживает потерю нескольких площадок), `HA-RACK-01/02` и `HA-QRM-03` (стойки), `DR-NET-03/04` (изоляция площадки не вызывает split-brain и не останавливает сервис).
Число площадок, которое проверяется «сразу», задаёт `requirements.siteFailures` (его ставит мастер) и ограничивает `engine.scenarios.maxSiteFailures` (4).

## Как смотреть на схему из многих площадок

Пять и десять площадок на одном холсте — это связи «каждый с каждым» (кворум, репликация, копии), и без помощи они сливаются в клубок. Что делает редактор:

* **Вкладка «Анализ → Площадки»** — карта площадок: по карточке на площадку, сгруппированы по домену отказа (`geo`); на карточке сервисы фишками продуктов (роль: `P` primary, `R` replica, `W` witness, `V` голос кворума), стойки, число компонентов, худшая открытая находка точкой
  и **вердикт симулятора на потерю этой площадки** — «сервис жив / деградация / недоступен», время и способ восстановления, RPO, ёмкость, «данные потеряны», split-brain (те же слова, что в карточке отказа и матрице отказов). «Показать» выделяет площадку на схеме и подводит холст, «Отказ» проигрывает потерю площадки.
  Карта строится из зон схемы, а не из результата мастера: роль берётся из `role` зоны, домен — из свойства `geo` зоны или её родителя. Меньше двух площадок — вкладка так и говорит.
* **Фокус.** Выбранный компонент подсвечивает свои связи и соседей на их концах, остальные связи и карточки отступают (кнопка «Фокус» на панели холста выключает это, выбор запоминается). Выбранная карточка видна при любом отдалении: рамка не уменьшается вместе с масштабом.
  Во время проигрывания отказа, показа находок и просмотра предложения ИИ фокус не работает: картинкой владеет другое.
* **Связи между площадками при отдалении** (компактные карточки и плитки) бледнеют, когда площадок не меньше `editor.quietEdgesSites` (4; 1 — всегда): остаются сами площадки и связи внутри них; выбранное и его связи яркие.
* Метки целей на вкладке «Проверки» не обрезаются — длинная метка переносится на вторую строку; названия эталонных схем в библиотеке занимают до двух строк.

## API

| Метод | Путь | Что |
|---|---|---|
| GET | `/placement/options` | схемы и та, что мастер предлагает первой (`defaultPattern`), платформы (слои, **продукты функции слоя и их варианты**, признак «управляемый»), типы площадок, пределы |
| POST | `/placement/preview` | `PlacementRequest` → `{architecture, sites, siteFailures, notes, report, nodes, edges}`; `report` — вердикт движка (оценка, счётчики, цели, стоимость, сценарии, худший запас ёмкости, главные замечания) |
| POST | `/placement/compare` | `{base, variants:[…]}` → `{variants:[{ok, pattern, sites, siteFailures, nodes, workingSites, arbiterSites, notes, report} \| {ok:false, error}]}` — до `limits.placementCompareMax` вариантов |
| POST | `/projects` | `{name, placement: PlacementRequest}` — проект создаётся по запросу размещения |

`PlacementRequest`: `pattern`, `sites`, `regions`, `racks`, `siteFailures`, `stack`, `layers` (включённые необязательные слои), `kinds` (слой → продукт), `variants` (слой → вариант продукта),
`requirements`, `siteType`, `lang`, `name`, `maxNodes`. Ошибки — `400 placement_failed` с `details.code`: `unknown_pattern`, `sites_out_of_range`, `unknown_tolerance`, `unknown_stack`, `unknown_kind`, `bad_kind`,
`unknown_variant`, `too_many_nodes`. Подробнее — [API.md](API.md).

## Настройка

Всё, что определяет результат, — данные в Администрирование → **Размещение**:

| Раздел | Что редактируется |
|---|---|
| **Схемы размещения** (`placement.pattern`) | допустимое число площадок, регионы, стойки, уровень отказа (`tolerance`), `siteFailures`, арбитры, резервные площадки, требования по умолчанию, платформа, плюсы и минусы для карточки |
| **Платформы** (`placement.stack`) | слои: продукт по умолчанию, функция, область, размер, число копий, связи, DCS |
| **Параметры генератора** (`placement.settings`) | схема, которую мастер предлагает первой (`defaultPattern`; неизвестная или выключенная — просто первая в списке, а в админке появится предупреждение), задержки и пропускная способность связей (`intraSite`, `intraGeo`, `interGeo`), имена зон, число голосов (`minVoters` / `maxVoters`), параметры арбитра и резервной площадки, предел узлов (`maxNodes`), `tlsBetweenSites` |

Кроме того: настройка `limits.placementCompareMax` (сколько вариантов сравнивать), `engine.scenarios` (`maxSiteFailures`, `maxCombinations`, `includeIsolation`, `isolationMaxSites`, `includeRacks`), `engine.tolerance`
(уровни отказа: экземпляр → стойка → площадка → регион).

Новую схему удобнее начать с копии ближайшей встроенной. Допустимо добавить схему «три ЦОД в двух регионах» или платформу без WAF и GSLB — код не меняется.

## Подводные камни

| Камень | Решение |
|---|---|
| Две площадки без третьей «побеждают» при разрыве канала | арбитр на третьей независимой точке добавляется автоматически (`witness: true`); без него замечание `no_authority` и ручное переключение |
| Кворум на чётном числе голосов | число голосов округляется вверх до нечётного, лишние — арбитры в независимых местах |
| Все копии данных в одной стойке или площадке | копии распределяются по местам по кругу, последняя — в резервной площадке; нехватка мест — `copies_limited` / `single_copy`, а не молчание |
| Десять площадок = сотни узлов | предел `maxNodes` (и лимит проекта) отсекает безразмерные схемы ошибкой `too_many_nodes`, а не зависшей вкладкой |
| Размер слоя «на глаз» | `sizing.mode: load`: экземпляры считаются из пика нагрузки и запаса роста, у каждого слоя своя доля нагрузки (`share`) |
| Управляемая БД требует etcd | вариант `managed` не требует DCS; слой DCS мастер подсказывает выключить («не нужно выбранным продуктам») |
| Между площадками разные задержки | профиль связей (`intraSite` / `intraGeo` / `interGeo`) становится свойствами связей; синхронная репликация возможна внутри региона, между регионами — асинхронная с лагом, который виден в RPO |
| Сгенерированное «зелёное» без проверки | результат всегда проходит движок; «нет данных» и риски показываются как есть, а не скрываются |
| Проект создаётся по устаревшему запросу | запрос повторно проверяется при создании проекта (`POST /projects` с `placement`): нельзя создать схему, которую `preview` отверг бы |
