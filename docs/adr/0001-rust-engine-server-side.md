# ADR-0001. Движок проверок — на Rust, на сервере

**Статус:** принято

## Контекст

Первоначальная концепция предлагала Go + OPA/Rego + AgentScope на бэкенде и ELK.js/Vue Flow на фронтенде. Позже требования уточнены: бэкенд на Rust,
фронтенд на Vue, всё в Docker. Ядро продукта — семантическая модель и проверки (симуляция отказов, кворум, RPO/RTO, ёмкость, стоимость). Оно
должно быть детерминированным, быстрым, покрытым тестами и использоваться одинаково из HTTP API, конвейера ИИ и экспорта.

## Решение

Ядро — отдельный crate `engine` без ввода-вывода (`backend/crates/engine`), сервер (`server`) лишь оборачивает его в HTTP и хранит данные.
Фронтенд **не дублирует** логику: проверки, симуляция, диффы, операции правки и экспорт выполняются на сервере; фронтенд вызывает
`/evaluate`, `/simulate`, `/ops/apply`, `/diff`. Правила — данные (ADR-0003), типы проверок — код.

## Последствия

* Один источник истины: нет расхождения между «что показал браузер» и «что проверил сервер/ИИ-конвейер».
* Rust даёт скорость и отсутствие данных-гонок; оценка и симуляция выполняются в `spawn_blocking`, не мешая I/O.
* Редактор зависит от сервера при каждой правке (отложенные, по умолчанию 350 мс — настройка `editor.evaluateMs`; запросы stateless и масштабируются репликами). Офлайн-режима нет.
* OPA/Rego не используется: проверки здесь — не политики над JSON, а вычисления над графом (симуляция, кворум), для которых типизированный
  код проще тестировать. Политики-как-данные дают правила `prop`, `forbidden_edge`, `path_contains`, `required_kind` — их можно менять в админ-панели.
