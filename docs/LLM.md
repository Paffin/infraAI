# ИИ и OpenRouter

Все модели подключаются через [OpenRouter](https://openrouter.ai): один ключ — любая модель. Выбор моделей, параметры запросов,
маршрутизация провайдеров, лимиты и бюджет — настройки в админ-панели (**Администрирование → OpenRouter** и **Настройки → ИИ**), пересборка не нужна.

## Принцип

LLM **не источник истины**. Она предлагает *операции над типизированной моделью*; корректность проверяет детерминированный движок
([RULES.md](RULES.md)). Модель не может изменить проект: результат — предложение, которое пользователь просматривает (diff на холсте,
изменение оценки, новые и закрытые замечания) и применяет явно; перед применением предыдущее состояние сохраняется версией.

## Виды запросов

| Вид | Что делает | Результат |
|---|---|---|
| `generate` | проектирует схему целиком по описанию (нагрузка, площадки, RTO/RPO, бюджет) | предложение `replace` (новая схема) |
| `patch` | вносит правку в текущую схему («добавь кэш», «сделай multi-region», «удешеви») | предложение `ops` (набор операций) |
| `fix` | исправляет конкретное замечание движка | предложение `ops` |
| `chat` | отвечает на вопрос о схеме и оценке | текст; доступен и роли `viewer` |

## Конвейер (`backend/crates/server/src/llm/pipeline.rs`)

1. **Подготовка контекста.** В промпт попадают каталог видов, типы связей и зон, список правил (чтобы модель знала критерии), шаблоны,
   текущая схема *без координат*, открытые замечания, требования. Заметки пользователя (`notes`) отправляются только при `llm.sendNotes`.
   Каталог — сотня продуктов, поэтому он **сжат**: общие свойства перечислены один раз, у вида — только своё (функция, поведение, признаки, роли, собственные значения и свойства, варианты строкой
   `id: Название [default] [behavior …] [+признаки]`); так весь каталог занимает долю прежнего объёма (тест следит, что он остаётся промптом). Модель выбирает продукт и ставит `props.variant`;
   `props.version` модель ставит **только если пользователь назвал версию**: заявленная версия проверяется по датам поддержки (`VER-01`), а придуманный моделью номер ничего не доказывал бы.
   Неизвестный вариант отклоняется валидацией (`unknown_variant`) и уходит в ремонт; об управляемых вариантах (`managed`) и вариантах с собственным кворумом (`self-quorum`) промпт говорит отдельно: им не нужен внешний DCS.
2. **Запрос.** `POST /chat/completions` с `response_format` по настройке `llm.structuredOutput`: `auto` (по умолчанию) отправляет строгую схему
   (`json_schema`) только там, где она целиком описывает ответ, а для генерации и правки — `json_object` (валидный JSON без схемы): в них есть
   свободные карты (свойства узлов, `set`), которые строгое декодирование выдаёт пустыми — на практике узлы приходили без свойств.
   `json_schema`, `json_object` и `prompt` (только инструкция) можно задать явно. Параметры, которые модель не поддерживает (например,
   `temperature` у Claude 5.x), не отправляются; если OpenRouter отвечает «No endpoints found», запрос повторяется в урезанном виде.
3. **Разбор и санитизация.** Извлечение JSON, приведение типов свойств к каталогу, отбрасывание неизвестных свойств, проверка ссылок
   (`unit_ref`), ограничение числа операций (`llm.maxOps`).
4. **Валидация и ремонт.** Структурные ошибки возвращаются модели с просьбой исправить (`llm.repairRounds`, 2 по умолчанию).
5. **Оценка движком и доработка.** Если остались критичные замечания, модель получает их и дорабатывает схему (`llm.refineRounds`).
6. **Автоисправления движка.** Оставшиеся замечания с безопасными детерминированными исправлениями (`llm.autoFixKinds`: масштабирование,
   DCS, witness, роли, группы) закрывает сам движок — без обращения к модели (`llm.autoFixRounds`).
7. **Предпросмотр.** Diff, оценка «до/после», `introduced` / `resolved` замечания — всё посчитано движком.

Пользователь видит шаги в строке запроса (подготовка → запрос к модели → проверка → доработка → автоисправления) и может отменить задачу.
Каждый шаг сохраняется в `ai_jobs.steps`; при `llm.logPrompts` в шагах остаётся и сырой ответ модели (для отладки; выключено по умолчанию).

## Модели

| Настройка | Назначение |
|---|---|
| `llm.model.planner` | генерация, правка, ремонт и доработка (по умолчанию `anthropic/claude-sonnet-5.5`) |
| `llm.model.fast` | быстрые вызовы — чат (по умолчанию `anthropic/claude-haiku-5.5`) |
| `llm.model.fallbacks` | список резервных моделей: OpenRouter переключается на них при недоступности основной |

Роль модели (`planner` / `fast`) задаётся в самом промпте (поле `role`), поэтому её можно менять в админ-панели для каждого шага.

Выбор модели — поиск по каталогу OpenRouter с ценой за 1M токенов и признаком поддержки структурированного вывода. Кнопка
«Проверить подключение» показывает ключ (лимит, остаток), существование выбранных моделей и предупреждения; «Проверить запросом»
отправляет запрос в 1 токен.

## Приватность (маршрутизация провайдеров)

Настройки `llm.provider.*` передаются в блок `provider` запроса:

* `dataCollection: deny` (по умолчанию) — только провайдеры, которые не хранят и не обучаются на ваших данных;
* `zdr` — только провайдеры с нулевым хранением (Zero Data Retention);
* `requireParameters` — только провайдеры, поддерживающие все переданные параметры (структурированный вывод);
* `sort`, `only`, `ignore`, `allowFallbacks` — приоритет цены/скорости и белый/чёрный списки провайдеров.

Ключ API хранится в БД зашифрованно (AES-256-GCM, ключ из `APP_SECRET`) или берётся из `OPENROUTER_API_KEY`; в API и интерфейсе он
не показывается — только «задан / источник».

## Контроль расходов и нагрузки

* **Месячный бюджет** `llm.monthlyBudgetUsd` (0 — без лимита): по достижении запросы отклоняются (`llm_budget`). Стоимость берётся из
  `usage.cost` ответа OpenRouter и записывается в `llm_calls`.
* **Лимит на пользователя** `llm.perUserPerHour`: превышение — `429 ai_rate_limited`.
* Одна активная задача на проект (`409 job_running`), ограничение длины запроса (`llm.maxPromptChars`), таймауты и повторы
  (`llm.timeoutSeconds`, `llm.retries`), потолок вывода (`llm.maxOutputTokens`).
* **Использование:** Администрирование → OpenRouter → расход по дням, моделям и пользователям; метрики `llm_calls_total`,
  `llm_cost_usd_total`.

## Промпты

Системные промпты (`generate`, `patch`, `chat`, `repair`, `refine`) — конфигурационные элементы вида `prompt`; их можно править в админ-панели
(форма с подсказкой по плейсхолдерам). Подстановки: `{{catalog}}`, `{{edge_types}}`, `{{zone_types}}`, `{{rules}}`, `{{templates}}`,
`{{requirements_schema}}`, `{{architecture}}`, `{{findings}}`, `{{report}}`, `{{errors}}`, `{{language}}`, `{{max_ops}}`. Панель
предупреждает о плейсхолдерах, которые сервер не заменяет. Сброс до встроенной версии — кнопкой «Сбросить».

## Ошибки

`llm_not_configured`, `llm_disabled`, `llm_budget`, `llm_auth`, `llm_credits`, `llm_rate_limited`, `llm_http`, `llm_timeout`, `llm_empty`,
`llm_truncated`, `invalid_output`, `interrupted` (реплика, державшая задачу, остановилась) — для каждой в интерфейсе есть понятное сообщение
на обоих языках, а в админ-панели — подсказка, что настроить.
