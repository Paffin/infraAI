# Проверка схем в конвейере: `infra-architect check`

Схема архитектуры — такой же артефакт, как код: она лежит в репозитории и меняется вместе с ним. `infra-architect check` даёт по ней вердикт, как линтер: **код выхода**, аннотации на изменённом файле,
отчёт в сводке задания, результаты во вкладке code scanning. Движок тот же, что в редакторе — правила, симулятор отказов, ожидаемая доступность, рекомендации, — поэтому одна и та же схема даёт и в редакторе,
и в конвейере одни и те же находки. Ничего не отправляется по сети, база данных и запущенный сервер не нужны.

```
$ infra-architect check architecture/shop.json --recommend
Интернет-магазин — architecture/shop.json
Оценка 70/100 · достоверность 100% · критично 3 · риск 0 · нет данных 0 · Доступность ≈ 99.8% (цель 99.95%) · Стоимость 727 900 ₽ в месяц

КРИТИЧНО  Оценка доступности — 99.8% при цели 99.95%: простои ≈ 10.1 ч в год при допустимых 4.4 ч (231% бюджета). Больше всего вносит «GSLB + CDN» (79%).
    AV-SLO-01 · Ожидаемая доступность укладывается в SLO
    Где: architecture/shop.json:66  gslb «GSLB + CDN»

КРИТИЧНО  Отказ «GSLB + CDN» останавливает сервис. Недоступно: GSLB + CDN.
    HA-SPOF-01 · Единых точек отказа нет
    Где: architecture/shop.json:66  gslb «GSLB + CDN»
    Исправление: Увеличить «GSLB + CDN» до 2 экземпляров

КРИТИЧНО  Отказ «WAF» останавливает сервис. Недоступно: WAF, GSLB + CDN.
    HA-SPOF-01 · Единых точек отказа нет
    Где: architecture/shop.json:80  waf «WAF»

Что улучшить в первую очередь

  - Открытых находок уровня «критично» и тяжелее: 3 (--fail-on critical)
$ echo $?
1
```

(Это настоящий вывод; «Где» — `файл:строка`, терминалы и редакторы превращают его в ссылку на место в файле.)

## Как запустить

Команда есть в том же исполняемом файле, что и сервер, и в образе:

```bash
# образ из реестра проекта (публикуется из main) — файлы схем монтируются в /work
docker run --rm -v "$PWD:/work:ro" -w /work ghcr.io/<владелец>/infra-architect:latest check architecture/shop.json

# или свой бинарник
cd backend && cargo build --release -p server && ./target/release/infra-architect check ../architecture/shop.json
```

В файле — схема (экспорт «JSON» из редактора) **или** объект с полем `architecture` (шаблон, выгрузка проекта). `-` читает стандартный ввод. Можно несколько файлов: вердикт один, решает худший.

## Параметры

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `--format <text\|json\|sarif\|markdown\|github>` | `text` | что печатается в стандартный вывод |
| `--report <формат>=<путь>` | — | дополнительно записать отчёт в файл; можно несколько раз. **Markdown дописывается** в конец (подойдёт `$GITHUB_STEP_SUMMARY`), остальные форматы файл заменяют |
| `--fail-on <critical\|risk\|no-data\|never>` | `critical` | уровень открытой находки, при котором проверка не пройдена; уровни вложены: `risk` — это критичные и риски, `no-data` — ещё и «нет данных» |
| `--min-score <0-100>` | — | не пройдено, если оценка ниже (ровно столько — проходит) |
| `--baseline <файл>` | — | не пройдено только из-за находок, которых не было в прошлый раз (JSON-вывод прошлого запуска или отчёт движка) |
| `--waivers <файл>` | — | принятые риски в файле рядом со схемой: JSON-список `{fingerprint, reason, by, at, expires}` (или объект со списком `waivers`) |
| `--recommend` | выкл. | добавить «что улучшить в первую очередь»: движок пробует каждое исправление на копии и измеряет эффект ([RECOMMENDATIONS.md](RECOMMENDATIONS.md)); каждое исправление — ещё одна проверка схемы, не больше `engine.recommendations.maxCandidates` |
| `--config <файл>` | как поставляется | резервная копия конфигурации экземпляра (Администрирование → Бэкап): его правила, каталог, настройки движка и лимиты |
| `--lang <ru\|en>` | язык конфигурации по умолчанию (`ru`) | язык текстов отчёта и сообщений |
| `--today <ГГГГ-ММ-ДД>` | сегодня, UTC | дата, на которую судятся сроки поддержки версий (движок не читает часы) |
| `--color <auto\|always\|never>` | `auto` | цвета текстового отчёта: на терминале, если не задан `NO_COLOR` |
| `-h`, `--help`, `-V`, `--version` | | справка (на языке `--lang`) и версия |

**Коды выхода:** `0` — пройдено · `1` — проверка не пройдена · `2` — проверить не удалось (неверный параметр, нечитаемый файл, это не схема, в схеме есть ошибки). Двойка — не «красный» конвейер, а «судить нечего»:
схема с ошибками (связь в никуда, неизвестный вид компонента) не получает вердикта, и стандартный вывод пуст.

## Что значит «не пройдено»

* **Уровень** (`--fail-on`) смотрит на открытые находки: принятые риски не считаются, но остаются в отчёте. `no-data` — вопросы, на которые движок не может ответить, потому что чего-то не задано (бюджет, измеренная задержка):
  в тексте у такой находки написано, что заполнить.
* **Оценка** (`--min-score`) — число от 0 до 100 из отчёта движка; удобна как нижняя планка рядом с уровнем.
* **База** (`--baseline`) нужна, чтобы подключить проверку к схеме с историей. Запишите `check --format json > baseline.json`; следующие запуски провалятся только на находках, которых там не было. Находка **известна**, если в базе
  была не мягче: то, что было риском, а стало критичным, — новое. Схема, которой в базе нет, — новая целиком: у неё нет истории, и проходить она должна полностью.
* **Принятые риски** (`--waivers`) — то же, что кнопка «Принять риск» в редакторе, только в файле: `fingerprint` находки (виден в JSON и в SARIF), `reason`, `by`, `expires`. Срок кончился — риск снова открыт, а отчёт
  говорит, какие принятия истекли. Дата не в формате `ГГГГ-ММ-ДД` — ошибка (код 2): опечатка не должна сделать принятие вечным.

## Форматы отчётов

| Формат | Для кого | Что внутри |
|---|---|---|
| `text` | человек в терминале и в логе | числа, находки (что не так, правило, `файл:строка`, исправление; для «нет данных» — что заполнить), «что улучшить в первую очередь», вердикт |
| `markdown` | сводка задания, комментарий к изменению | заголовок с вердиктом, таблица находок, таблица рекомендаций с эффектом |
| `github` | аннотации GitHub Actions | `::error` / `::warning` / `::notice` с файлом и строкой: видны на изменённых строках и в сводке проверки |
| `sarif` | code scanning (GitHub, GitLab, Azure DevOps, IDE) | SARIF 2.1.0: правила с описанием, почему важно и что делать; результат на каждую находку с уровнем (`error` / `warning` / `note`), строкой элемента в файле, отпечатком для сопоставления между запусками, подписями исправлений и недостающих полей в свойствах; принятые риски — как `suppressions` |
| `json` | скрипты, база сравнения | `{version, passed, results: [{file, name, passed, verdict, report, plan?}]}`; `report` — тот же отчёт, что отдаёт `POST /evaluate` ([API.md](API.md)) |

SARIF указывает на строку элемента: движок находит в файле первое `"id": "…"` с идентификатором узла, связи или зоны (в минифицированном файле это строка 1). Пути — относительные, с `/`, без `./`, с экранированием
пробелов: запускайте из корня репозитория и давайте пути от корня.

## Конфигурация экземпляра

Без `--config` схема судится правилами, каталогом и настройками, поставляемыми в программе. Если в вашей установке правила настроены (отключено правило, изменена серьёзность, свой продукт в каталоге, другие частоты отказов в
`reliability`, свои лимиты), скачайте **резервную копию конфигурации** (Администрирование → Бэкап, [ADMIN.md](ADMIN.md)) и дайте её `--config`: конвейер будет судить так же, как редактор. Копия проверяется поэлементно так же, как
правка администратора, и при любой ошибке отвергается целиком с указанием, какой элемент не годится, а не применяется наполовину. Секреты в копию не попадают.

## Примеры конвейеров

**GitHub Actions** — вердикт в сводке, аннотации на файле, находки во вкладке code scanning:

```yaml
name: Architecture
on:
  pull_request:
    paths: ["architecture/**"]
permissions:
  contents: read
  security-events: write          # загрузка SARIF
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Проверить схемы
        run: |
          docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/work" -v "$GITHUB_STEP_SUMMARY:/summary" -w /work \
            ghcr.io/<владелец>/infra-architect:latest check architecture/*.json \
            --recommend --format github --report sarif=architecture.sarif --report markdown=/summary
      - uses: github/codeql-action/upload-sarif@v3
        if: always() && hashFiles('architecture.sarif') != ''
        with:
          sarif_file: architecture.sarif
```

**Только новое** — схема с историей: основа лежит в репозитории, обновляется осознанно (`check … --format json > architecture/baseline.json`):

```yaml
      - run: |
          docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/work" -w /work ghcr.io/<владелец>/infra-architect:latest \
            check architecture/shop.json --baseline architecture/baseline.json --min-score 70
```

**GitLab CI** (в образе нужен свой вход вместо `ENTRYPOINT`):

```yaml
architecture:
  image:
    name: ghcr.io/<владелец>/infra-architect:latest
    entrypoint: [""]
  script:
    - /app/infra-architect check architecture/*.json --recommend --report json=report.json --report markdown=report.md
  artifacts:
    when: always
    paths: [report.json, report.md]
```

**pre-commit** — до коммита, с уровнем строже:

```yaml
repos:
  - repo: local
    hooks:
      - id: architecture
        name: architecture
        entry: infra-architect check --fail-on risk --lang en
        language: system
        files: ^architecture/.*\.json$
```

## Подводные камни

| Что могло пойти не так | Как решено |
|---|---|
| Схема с ошибками «проходила» бы: нечего проверять — нет находок | вердикта нет вообще: код 2, причина в стандартном потоке ошибок, стандартный вывод пуст; в одном запуске с исправными схемами отчётов тоже нет — один запуск, один вердикт |
| Принятый риск живёт вечно: про него забыли | `expires`; истёк — риск снова открыт и назван в отчёте; недата — ошибка, а не «бессрочно» |
| База скрывает ухудшения: «это уже было» | известна только находка, которая в базе была не мягче; риск, ставший критичным, — новая |
| Новую схему пустили без проверки, потому что базы для неё нет | у схемы без записи в базе нет истории: все её находки новые |
| SARIF без места в файле не показывается во вкладке code scanning | строка элемента ищется в исходном файле; без строки результат указывает на начало файла; пути нормализуются (`\` → `/`, `./`, пробелы) |
| Сводка задания затёрта: в файл пишут и другие шаги | отчёт `markdown` дописывается, остальные форматы заменяются |
| В заголовке «критично 2», а ниже три находки | в заголовке — открытые находки, которые перечислены ниже; счётчики по правилам остаются в `report.counts` |
| Конвейер зависит от часов: сроки поддержки версий «тикают» | `--today` фиксирует дату; движок часов не читает |
| Чужая конфигурация применилась бы наполовину | резервная копия проверяется поэлементно и отвергается целиком вместе с причиной |
| Цвета в логе CI превращаются в мусор | цвет только на терминале и без `NO_COLOR`; `--color always` включает осознанно |
| `| head` закрывает вывод — программа падает | закрытый канал не считается ошибкой проверки |
| «Отправляет ли это мою схему куда-нибудь?» | нет: команда читает указанные файлы и ничего не открывает по сети; ключей и базы не нужно (дочерний процесс в тестах запускается с пустым окружением) |

## Тесты

`crates/engine/tests/gate.rs` — на настоящем движке: уровни и вложенность, оценка, принятые риски и истечение, база (известное, новое, ухудшившееся, чужой файл), тексты на двух языках, Markdown, аннотации, структура SARIF.
`crates/server/tests/cli.rs` — настоящий бинарник с пустым окружением: коды выхода, пороги, входные ошибки, стандартный ввод и обёртка шаблона, JSON как база следующего запуска, принятые риски, отчёты в файлы, несколько схем, конфигурация экземпляра,
справка; **каждая поставляемая эталонная схема проходит свой собственный шлюз**. `deploy/check-sarif.py` проверяет SARIF по официальной схеме OASIS (в CI — для всех эталонных схем).
