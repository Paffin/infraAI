# Архитектура

## Принцип

> **LLM предлагает, движок доказывает, человек решает.**

Всё в продукте вращается вокруг одной модели — типизированного графа архитектуры (*цифровой двойник*). Схема на холсте, чат с ИИ,
проверки, симуляция отказов, оценка стоимости и экспорт (Kubernetes, Helm, Terraform, ADR, Runbook) — **представления** этой модели. Любое изменение —
ручное, предложенное ИИ или исправление движка — проходит одну и ту же валидацию и одну и ту же проверку.

```
 Браузер (Vue 3, Vue Flow, Pinia)
   │  HTTP/JSON, cookie-сессия
   ▼
 Сервер (Rust, axum) ── stateless, N реплик за балансировщиком
   ├─ api/        аутентификация, проекты/версии, движок, ИИ, админка
   ├─ llm/        клиент OpenRouter, промпты, конвейер генерации
   ├─ engine/     (отдельный crate, чистая логика без I/O)
   │    model · catalog · graph · sim · checks · evaluate · ops · cost · export
   └─ PostgreSQL  проекты, версии, настройки, правила/каталог/промпты, задачи ИИ, аудит
```

## Модель данных (`engine::model`)

* **Architecture** — `zones[]`, `nodes[]`, `edges[]`, `requirements`, `meta`. Версия схемы `schemaVersion`.
* **Zone** — домен отказа: `dc`, `cloud`, `az`, `region`, `rack`, `group`; вложенность через `parentId`; `role` (`active`/`standby`/`witness`),
  `props.geo` (гео-домен: площадки с одним значением гибнут вместе при катастрофе района).
* **Node** — компонент (`kind` из каталога), `zoneId`, `group` (узлы одной группы — один сервис/кластер, взаимозаменяемы), `role`, `props`.
* **Edge** — связь с семантикой по типу: `dependency` (трафик), `replication` (sync/async), `membership` (кворум), `backup`, `control`.
* **Requirements** — RPS, рост, RTO, RPO, SLO, бюджет, «какой отказ нужно переживать» (`instance`/`site`/`geo`), комплаенс, заметки.
* Положение на холсте (`ui`) — часть данных, но не часть архитектуры: diff и проверки его игнорируют.

Всё, что описывает *виды* компонентов, типы связей и зон, правила, шаблоны, промпты и допущения движка — **данные**, а не код (см.
[ADR-0003](adr/0003-data-driven-configuration.md)). Встроенные значения лежат в `backend/crates/engine/defaults` и
`backend/crates/server/defaults` и при первом запуске копируются в PostgreSQL; дальше их можно менять в админ-панели.

## Движок (`backend/crates/engine`)

Чистая библиотека: никаких сетей, часов и случайности — результат определяется только входом, поэтому проверки воспроизводимы и
тестируются на эталонных архитектурах с известными дефектами.

| Модуль | Назначение |
|---|---|
| `catalog` | виды компонентов, типы связей и зон, свойства; эффективные свойства (значения по умолчанию + заданные) |
| `graph` | индекс графа: *юниты* (группы узлов), цепочки зон, площадки, гео-домены, пути запросов |
| `sim` | симулятор отказов ([SIMULATION.md](SIMULATION.md)) |
| `checks` | 26 типов проверок, на которых строятся правила ([RULES.md](RULES.md)) |
| `evaluate` | прогон правил, оценка (score) и достоверность, цели RTO/RPO/площадка/SPOF/ёмкость, принятые риски |
| `ops` | атомарные операции правки (`add_node`, `update_edge`, …), валидация результата, diff |
| `cost` | оценка стоимости из прайса в настройках |
| `export` | ADR, Runbook, Mermaid, JSON; точка входа всех форматов |
| `iac` | IaC из модели: план развёртывания (кластеры, размещение, площадки), язык шаблонов (minijinja), записи YAML/HCL, отчёт о покрытии ([IAC.md](IAC.md)) |
| `text` | локализуемые тексты `{ru,en}` и подстановки `{x}`, `{x\|dur}`, `{x\|pct}` |

## Сервер (`backend/crates/server`)

* **Stateless.** Состояние — только в PostgreSQL. Сессия — подписанная HMAC cookie (`ia_session`, HttpOnly, SameSite=Lax); на каждый
  запрос роль и актуальность сессии сверяются с кэшем пользователей (10 с). Любая реплика обслуживает любой запрос.
* **Конфигурация без перезапуска.** Правила, каталог, шаблоны, промпты, настройки читаются из БД и кэшируются; счётчик ревизии
  (`meta.config_rev`) увеличивается при каждом изменении, остальные реплики замечают это за секунды и перезагружают кэш.
* **Старт под advisory-lock.** Миграции, посев встроенных элементов, администратор по умолчанию и демо-проект выполняются под
  `pg_advisory_lock` — одновременный старт трёх реплик безопасен. Обновление встроенного элемента не затирает изменённые вручную
  (элементы помечены хэшем и флагом `modified`; при расхождении появляется `updateAvailable`).
* **Задачи ИИ в БД.** Запрос к модели — задача `ai_jobs` с шагами и heartbeat. Реплика, взявшая задачу, обновляет heartbeat; задача
  умершей реплики помечается упавшей фоновым «уборщиком» на другой реплике, пользователь видит `interrupted`, а не вечную крутилку.
* **Оптимистичная конкуренция.** Черновик проекта сохраняется с `expectedRev`; при конфликте — `409 conflict` с текущей ревизией.
  Версии — явные снимки (`POST /versions`) и автоматические вокруг применённых предложений ИИ.
* **Graceful shutdown.** По SIGTERM `/readyz` сразу начинает отвечать 503 (балансировщик выводит реплику из ротации), через
  `DRAIN_SECONDS` сервер перестаёт принимать соединения, активные задачи ИИ дорабатывают до `SHUTDOWN_GRACE_SECONDS`.
* **Безопасность.** Argon2id для паролей; блокировка после серии неудачных входов; лимит попыток входа по IP; проверка `Origin`
  (CSRF) для изменяющих запросов; строгий CSP (`script-src 'self'`); роли `viewer < editor < admin`; секреты в БД шифруются AES-256-GCM
  ключом из `APP_SECRET` и никогда не возвращаются API; журнал аудита; временный пароль открывает только смену пароля.
* **Наблюдаемость.** JSON-логи, `/healthz` (процесс жив), `/readyz` (БД доступна и сервер не гасится), `/metrics` (Prometheus).

## Поток «описал → получил → проверил → применил»

1. Пользователь вводит запрос; `POST /projects/{id}/ai/jobs` создаёт задачу, фронт опрашивает её раз в секунду.
2. Конвейер ([LLM.md](LLM.md)): подготовка контекста → запрос модели (структурированный вывод) → разбор и санитизация → валидация →
   *ремонт* ответа при ошибках → оценка движком → *доработка* по критичным замечаниям → автоисправления движка →
   предпросмотр (diff, до/после).
3. Результат — `proposal`. Он **не меняет** проект. Холст показывает предпросмотр поверх схемы (добавленное — пунктиром,
   удалённое — бледным), правая панель — diff и изменение оценки.
4. «Применить» — сервер сохраняет предыдущее состояние версией, применяет операции к *текущему* черновику (если схема за это время
   изменилась и операции не применяются — предложение помечается устаревшим) и отвечает новой ревизией.

## Фронтенд (`frontend/`)

Vue 3 + TypeScript, Pinia, Vue Flow. Дизайн-токены (`src/styles/tokens.css`) сняты с макета и переопределяются настройкой `ui.theme`.

* `stores/editor.ts` — единственный источник правды редактора: схема (неизменяемые снимки), история отмены, автосохранение
  (900 мс, повтор при сетевых сбоях, обработка `409`), вычисление проверок (350 мс, отмена устаревших запросов), симуляция, предпросмотр.
* `editor/layout.ts` — детерминированная авто-раскладка: ряды по глубине зависимостей, площадки — колонки одной высоты, одинаковые
  компоненты соседних площадок выровнены и «зеркалятся», чтобы связи репликации были короткими. Новые узлы без координат
  размещаются в свободных слотах своей зоны ([ADR-0005](adr/0005-layout-without-elk.md)).
* `editor/flowModel.ts` — перевод модели (абсолютные координаты) в модель Vue Flow (зоны — родительские узлы); объекты переиспользуются,
  пока координаты не изменились.
* Всё, что видит пользователь, берётся из каталога и правил, пришедших в `/bootstrap`: подписи компонентов, свойства инспектора,
  тексты замечаний. Хардкода предметной области во фронтенде нет.
* Администрирование — `src/admin/`, отдельный чанк; формы строятся из реестра настроек.

## Масштабирование и отказоустойчивость самого сервиса

* **Горизонтально.** Реплики идентичны; нагрузка — в основном CPU на оценке/симуляции (выносится в `spawn_blocking`) и ожидание модели.
  HPA по CPU, распределение по зонам (`topologySpreadConstraints`), `PodDisruptionBudget`.
* **База.** Единственное stateful-звено. Для продакшена — PostgreSQL с автоматическим переключением и PITR (пример на CloudNativePG —
  `deploy/k8s/postgres-cnpg.example.yaml`). Сервис терпит кратковременную недоступность БД: `/readyz` выводит реплики из ротации,
  `/healthz` не перезапускает здоровые поды.
* **Катастрофа.** Всё состояние продукта — в PostgreSQL (проекты, версии, настройки, правила). Восстановление = восстановить БД +
  поднять образ с тем же `APP_SECRET`. Подробности и целевые RPO/RTO — [DEPLOYMENT.md](DEPLOYMENT.md).
