# Движок проверок

Правила — это **данные** (`rules.json`, редактируются в админ-панели) поверх 29 готовых, покрытых тестами типов проверок. Правило задаёт
тип проверки, параметры, серьёзность, вес и тексты (на каждом языке): заголовок, сообщение, «почему это важно», подписи кнопок исправления.
Нового кода для типового правила не нужно — см. [DEVELOPMENT.md](DEVELOPMENT.md).

## Статусы

| Статус | Значение |
|---|---|
| `critical` | предпосылка надёжности нарушена |
| `risk` | серьёзный недочёт, который стоит исправить |
| `no_data` | проверить нельзя: нет данных или значение взято из допущения. **Не «зелёный»** |
| `ok` | проверено и выполняется |
| `na` | неприменимо к этой схеме (нет площадок, нет баз данных, …) |

Двигатель никогда не показывает «зелёное» там, где предпосылки не проверены: незаданные требования (RTO, RPO, RPS), RTT без замера,
асинхронный лаг по умолчанию, «по допущениям» — всё это `no_data`.

## Оценка

```
score = 100 − Σ штрафов     штраф: critical = 15, risk = 4, no_data = 1.5 (суммарно не больше 12)
```

Веса берутся из `engine.scoring` и могут быть переопределены для правила полем `weight`. Принятые риски не снижают оценку.
Рядом с оценкой — **достоверность**: доля применимых правил, проверенных по данным, а не по допущениям. Оценка детерминирована и не
зависит от ИИ; ИИ может лишь предложить изменения, после которых оценка пересчитывается заново.

## Находки

Каждая находка имеет стабильный **отпечаток** (`HA-CACHE-02:redis:dc1`), по которому работают принятые риски. Находка содержит `vars` для
подстановки в тексты, `subjects` (узлы/связи/зоны — для подсветки «Показать на схеме»), `scenario` (какой отказ воспроизвести) и список
**исправлений** — детерминированных наборов операций (`add_member`, `add_witness`, `set_dcs`, `scale`, `add_backup`, `make_sync`, …).
«Исправить» применяет операции атомарно; результат — обычная правка схемы с отменой и повторной проверкой.

## Принятие риска

Для `critical` и `risk` (не для `no_data`) редактор может **принять риск**: обоснование (не короче `limits.waiverMinReasonChars`) и срок
(не больше `limits.waiverMaxDays`). Принятая находка остаётся видимой, помечена автором и датой, не снижает оценку и попадает в ADR.
Срок истёк или находка изменилась (другой отпечаток) — риск возвращается в работу.

## Типы проверок

| Тип | Что проверяет |
|---|---|
| `spof` | единые точки отказа: отказ любого узла/экземпляра на пути запроса не должен останавливать сервис |
| `survive_site` | сервис переживает потерю любой одной площадки (с параметром `domain: rack` — стойки) |
| `survive_sites` | сервис переживает **одновременную** потерю нескольких площадок (`k` из требований, до `engine.scenarios.maxSiteFailures`) |
| `rto` / `rpo` | время восстановления и потеря данных при потере площадки укладываются в требования; потеря данных безвозвратно — нарушение RPO |
| `geo_survive` / `geo_spread` | катастрофа гео-домена (город/район) и разнесение площадок по доменам |
| `partition_safety` | разрыв канала между площадками не приводит к split-brain / двум писателям |
| `min_instances` / `spread_sites` | минимальное число экземпляров и разнесение по площадкам для видов с заданным свойством |
| `quorum_voters` / `witness_independent` | нечётное число голосов, арбитр на независимой площадке |
| `replication_policy` | политика репликации хранилищ (синхронная/асинхронная, митигации, RTT синхронных связей) |
| `failover_authority` | у автопереключения есть арбитр: внешний DCS, witness, собственный кворум продукта (`self-quorum`) или провайдер (`managed`, `platform-quorum`), иначе небезопасно |
| `backup_exists` / `backup_offsite` | у данных есть резервная копия, вне площадки хранения, неизменяемая, проверенная восстановлением. Копия «вне» относительно запрошенного уровня: при уровне «стойка» (схема в одном ЦОД) копия в другой стойке — `риск`, в той же стойке — критично; при «площадке» и выше — копия на той же площадке критична |
| `prop` | значение свойства компонента (TLS, шифрование, версии, интервалы …); самый универсальный тип |
| `capacity` / `capacity_under_failure` | ёмкость покрывает пик с запасом и при потере площадки |
| `cost_budget` | оценка стоимости укладывается в бюджет |
| `availability_slo` | ожидаемая доступность ([AVAILABILITY.md](AVAILABILITY.md)) не хуже целевой: `критично` — простоя больше допустимого, `риск` — больше `reliability.warnPercent` допустимого, `нет данных` — цель не задана или часть отказов не рассмотрена |
| `path_contains` / `forbidden_edge` / `required_kind` / `role_required` | структурные: обязательное звено на пути, запрещённая связь, обязательный вид, роль у узла |
| `no_cycles` | нет циклических жёстких зависимостей |
| `cache_resilience` | потеря кэша не обрушивает базу (репликация кэша, поведение холодного кэша) |
| `group_hygiene` | параллельные узлы одного вида объединены в группу (иначе движок считает их независимыми сервисами) |
| `version_lifecycle` | версия продукта, **заявленная в узле**, ещё получает исправления безопасности по таблице выпусков; параметры `warnDays`, `onMissing`, `onUnknown` ([CATALOG.md](CATALOG.md)) |
| `version_skew` | члены одного кластера работают на одной линии выпуска |
