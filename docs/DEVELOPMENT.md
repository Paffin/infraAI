# Разработка

Всё запускается в контейнерах, ничего ставить на хост не нужно:

```bash
make test            # cargo test --workspace (с PostgreSQL) + typecheck/vitest/build фронтенда
make up              # пишет .env со случайными секретами, собирает образ и запускает приложение + БД: http://localhost:8080
make try             # то же без сборки, из готового образа (IA_IMAGE; deploy/compose.try.yml)
make iac-check       # IaC эталонных архитектур против схем Kubernetes/CRD, Helm и Terraform (см. IAC.md)
```

Без `make`: `sh deploy/init-env.sh` пишет `.env` (его же вызывает `make .env`), `sh deploy/check-env.sh` проверяет, что быстрый старт цел (в CI — задание `docs`). Без Docker: Rust 1.89+ (stable), Node 22, PostgreSQL 14+.

## Бэкенд

```bash
cd backend
export TEST_DATABASE_ADMIN_URL=postgres://postgres@localhost:5432/postgres   # для интеграционных тестов: каждому тесту — своя БД
cargo test --workspace
cargo fmt --all --check && cargo clippy --workspace --all-targets -- -D warnings
```

Кластер PostgreSQL — в кодировке **UTF8** (`initdb --encoding=UTF8`; образ `postgres` и пакеты дистрибутивов делают так сами). Кластер из голого `initdb` под локалью `C` — `SQL_ASCII`: `left()` там считает байты, срез русского описания посреди буквы PostgreSQL отдать не может, и тест `budgets::list_stays_small_with_long_descriptions` (как и список проектов на такой базе) падает с `invalid byte sequence`. Сервер на такой базе предупреждает при старте.

Запуск сервера для разработки:

```bash
export APP_ENV=development DATABASE_URL=postgres://postgres@localhost:5432/infra_dev ADMIN_EMAIL=admin@dev.local ADMIN_PASSWORD='dev password 123456'
cargo run -p server          # слушает :8080; без APP_SECRET в development используется временный
```

Структура: `crates/engine` — чистая логика (без I/O), `crates/server` — HTTP, БД, ИИ.

### Тесты без моков и заглушек

В тестах нет двойников внешних сервисов:

* **чистые функции** — формирование запроса к OpenRouter (`build_body`), разбор ответа (`interpret`), разбор и проверка ответа модели
  (`parse_generate`, `parse_patch`) тестируются на **настоящих** данных: ответы OpenRouter и модели записаны живыми прогонами
  (`crates/server/tests/fixtures/llm`, запись — `LIVE_LLM_RECORD=<каталог>`);
* **интеграционные тесты** (`crates/server/tests/api.rs`) поднимают настоящий роутер на настоящем PostgreSQL (своя БД на тест): ошибки сети,
  бюджет, лимиты, предложения (просмотр, применение, устаревание, откат) — без обращения к модели;
* **соединения и гонки** проверяются настоящей базой, без пауз и подмен: `TestApp::with_pool(1)` — то же приложение на пуле из одного соединения (обработчик, которому нужны два сразу, падает по таймауту через две секунды, а не виснет под нагрузкой); сдвиг черновика посреди применения
  воспроизводит сам тест — держит блокировку строки проекта, ждёт в `pg_stat_activity`, пока применение встанет за ней, делает свою запись и отпускает (`while_the_apply_waits`);
* **сокеты, которые ведут себя плохо нарочно** — `outbound::hostile` (юнит-тесты `versions::` и `outbound::`) и `Hostile` в `tests/budgets/mod.rs`: слушатель на `127.0.0.1`, который по-ручному говорит HTTP/1.1, считает запросы и отвечает перенаправлением на адрес вне списка или
  бесконечным ответом без длины. Это не двойник сервиса: настоящий источник нельзя попросить перенаправить туда, куда не следует, или отвечать вечно, а что делает клиент тогда, и проверяется. У такого теста всегда есть контроль, доказывающий, что ловушка работает
  (клиент, который идёт за перенаправлением, как прежний, попадает на второй слушатель: один запрос, у `versions::fetch` — ноль); а новые тесты бюджетов лежат в `tests/budgets/mod.rs` (подключён из `api.rs`: каталог с `mod.rs` не становится ещё одним тестовым бинарником);
* **медленный клиент и срок запроса** — `slow_header_connection_is_closed` (в `tests/budgets/mod.rs`) поднимает `server::serve::run` — цикл соединений, которым пользуется `main.rs` — на настоящем слушателе с настоящим роутером: сокет с полстрокой заголовка закрыт за 2 с, обычный запрос на том же слушателе отвечен,
  адрес партнёра дошёл до обработчика (`ConnectInfo`), а без срока тот же сокет остаётся открытым; срок запроса проверяет `a_request_that_takes_too_long_is_answered_in_json_after_the_deadline` на настоящей блокировке строки проекта (тест держит её в своей транзакции), а не на подставленном «медленном» маршруте;
* **настоящие сокеты** — `tests/metrics_port.rs` поднимает слушатель метрик тем же `api::bind_metrics` и `api::serve_metrics`, что и `main.rs`, и ходит к нему `reqwest` (`TestApp::with_boot` меняет загрузочную конфигурацию: порт метрик, токен, веб-каталог). Веб-каталог теста — временный, с `index.html`
  (`temp_web_dir`): без него «нет маршрута» тоже `404`, и проверка «порт приложения отвечает `404`, а не страницей приложения» прошла бы без самой возможности;
* **несколько реплик и одновременные запросы** — тоже настоящие: `TestApp::second_instance()` поднимает второй экземпляр над той же базой (общего у них только PostgreSQL), `login_from(адрес, заголовки, …)` приходит с другого адреса
  (и с `X-Forwarded-For`), `metric("infra_…")` читает `/metrics`, `with_hash_slots(n)` ставит затвор хэширования на n мест (тест держит место и смотрит, что вход, смена и сброс пароля и создание пользователя ждут его). Гонки (двадцать входов сразу) идут на
  `#[tokio::test(flavor = "multi_thread", worker_threads = 4)]` и проверяют **итог** (сколько паролей проверено, чем кончилась блокировка), а не время; окно и срок блокировки двигаются SQL над `rate_limits`, без пауз. Argon2 в отладочной сборке
  собирается с `opt-level = 3` (`[profile.dev.package.argon2]` в `backend/Cargo.toml`): иначе вход стоит полсекунды, а набор входит десятки раз;
* **живые тесты** (`crates/server/tests/live.rs`, `#[ignore]`) — настоящий OpenRouter: связь и каталог моделей, чат, патч с применением,
  генерация. Стоят центы, идут около минуты:

```bash
OPENROUTER_API_KEY=sk-or-… cargo test -p server --test live -- --ignored --nocapture     # LIVE_LLM_MODEL=… выбирает модель
```

* **IaC** проверяется настоящими инструментами: `make iac-check` ([IAC.md](IAC.md)).
* **Трафик при отказе** (`crates/engine/tests/traffic.rs`, [SIMULATION.md](SIMULATION.md)) — на всех поставляемых шаблонах: в штатной работе каждая связь несёт свою долю и ничего не теряется; потоки складываются в нагрузки модели ёмкости там, где ничего не застряло и не перегружено; ни одна связь не несёт больше, чем получает её источник; при потере ЦОД трафик гибнет у базы, пока реплику не повысили; балансировщик шлёт в упавшего участника, пока не заметит, потом трафик идёт в обход; разорванный канал ничего не несёт; картина не противоречит состояниям узлов. Поля `traffic` и `trafficBefore` в `/api/simulate` проверяет `crates/server/tests/api.rs`.
* **Проверка в конвейере** (`infra-architect check`, [CLI.md](CLI.md)): `crates/engine/tests/gate.rs` — на настоящем движке; `crates/server/tests/cli.rs` запускает **настоящий бинарник** с пустым окружением на файлах во временном каталоге
  (коды выхода, форматы, база, принятые риски, `--config`); каждая поставляемая эталонная схема должна проходить свой шлюз. SARIF сверяется с официальной схемой: `python3 deploy/check-sarif.py файл.sarif` (нужен `pip install jsonschema`).
  Вручную: `cargo run -q -p server -- check ../файл.json --recommend`.

## Фронтенд

```bash
cd frontend
npm ci
API_TARGET=http://localhost:8080 npm run dev      # Vite на :5173 с прокси /api
npm run typecheck && npm test && npm run build
```

* Цвета и размеры — только из `src/styles/tokens.css`; компоненты используют CSS-переменные, hex-значений в компонентах нет. Цвета текста (`--muted`, `--faint`, `--label`, `--ok`, `--risk` …) держат
  контраст не ниже 4.5:1 на своих поверхностях (проверяет `e2e/a11y.spec.ts`).
* Тексты — только через `t()` / `lt()`; ключи в `src/i18n/{ru,en}.ts` (редактор) и `{ru,en}.admin.ts` (админка). Тест
  `tests/i18n-keys.test.ts` проверяет, что все ключи есть в обоих языках и что нет неопределённых.
* Предметная область (виды, свойства, тексты замечаний) приходит из `/bootstrap`, а не из кода.
* e2e: тесты стартуют как пользователь, отключивший туры и скрывший подсказку «ИИ выключен» (`e2e/fixtures.ts`; `tour.spec` и `ai-off.spec` возвращают своё), и сами удаляют созданные проекты (и сделанные через API помощником `projectWith`), поэтому долгоживущий стенд не упирается в `limits.maxProjectsPerUser`.
  Свои тесты импортируют `test` из `./fixtures`, а не из `@playwright/test`.
* **Окно берёт клавиатуру, держит её и возвращает.** Новое окно строят на `components/Modal.vue` (не окно, как палитра, — на `lib/useFocusScope.ts`): оно переводит фокус в себя (в поле с `autofocus`, иначе в первое действие тела, затем подвала), делает всё остальное в `body` `inert`
  (счётчик на элемент, `lib/inert.ts`: окно, второе окно и тур не снимают блокировку друг у друга), замыкает Tab и Shift+Tab на концах и при закрытии возвращает фокус тому, что был в фокусе при открытии. Esc слышит только верхнее окно: свой `keydown` по Esc в новом окне
  закрыл бы два окна сразу. Что окно поднимает поверх себя (сообщение) лежит в `body` и помечено `data-keep-live`. Заголовок вкладки пишет один эффект (`App.vue` и `lib/pageTitle.ts`): `document.title` больше нигде не присваивают (тест `tests/pageTitle.test.ts` следит); после перехода на новую страницу фокус идёт на её `h1`.
* Путь сохранения при потере связи и конце сессии проверяет `e2e/session.spec.ts` (`setOffline`, `clearCookies`: полоса «нет связи» не налезает на панель инструментов и на 1440 px, повтор сразу после `online`, копия несохранённых правок в `localStorage`, предложение восстановить, «Открыть как новый проект», выход из системы убирает копию); войти на странице входа, на которую приложение
  перебросило само, помогает `loginTo` из `e2e/helpers.ts` (`login` ждёт список проектов). Чистые части — `tests/saveQueue.test.ts`, `tests/history.test.ts`, `tests/unsavedBackup.test.ts` на настоящем `localStorage` jsdom с его квотой.
* Панели и окна проверяют `e2e/panels.spec.ts` (рейка и ширина правой панели, перетаскивание и сворачивание «Что если отказа» и окна отказа, запоминание положения, клавиатура) и `e2e/simpanel.spec.ts` (плитки, список затронутых,
  столбики шагов, ссылка и Markdown, `?sim=`, «Несколько сразу…»); у перетаскивания настоящие события указателя, а проверки ждут конца анимации появления окна.
* Библиотека каталога проверяется целиком (`crates/engine/tests/products.rs`: каждый продукт и каждый способ его запуска ставится на схему, проходит проверку и симуляцию отказа, сервис провайдера не получает правил про «два экземпляра»;
  `placement.rs`: мастер строит чистую схему для каждого продукта слоя на 1–10 площадках, продукты, которые по своей природе не могут, перечислены в `KNOWN_LIMITS` с причиной). Добавили продукт — эти тесты уже его проверяют.
* **Тесты фронтенда тоже без заглушек.** Чистая логика (`lib/needs`, `lib/objectives`, `lib/capacity`, `lib/diagram`, раскладка) проверяется
  на **настоящем выводе движка**: `tests/fixtures/*.json` — это `{architecture, report}`, записанные примером движка
  (`deploy/record-fixture.sh <шаблон | файл.json> <имя>`; `FIXTURE_TODAY=…` даёт движку дату для правил версий; `FIXTURE_PLAN=1` записывает вместо отчёта план «что улучшить в первую очередь» — `{architecture, plan}`; фикстуры, зависящие от таблиц выпусков, перезаписывает `deploy/rerecord-fixtures.sh`;
  вердикты жизненного цикла для сверки порта на TypeScript с движком — `cargo run -p engine --example lifecycle`; **истории отказов** с трафиком — `{architecture, scenario, result}` от `simulate_timeline`, запись — `deploy/record-sim.sh <шаблон | файл.json> '<сценарий>' <имя>`), и настоящий каталог из `backend/crates/engine/defaults`
  ([README фикстур](../frontend/tests/fixtures/README.md)). Изменился JSON-ответ движка — тест падает здесь, а не в браузере. Тест
  «каждая потребность (`needs`), которую выдаёт движок, ведёт на редактируемое свойство» ловит рассинхрон каталога и правил.
  Единственные двойники в тестах фронтенда — два хранилища в `tests/unsavedBackup.test.ts`: одно бросает исключение на любой вызов (хранилище, запрещённое настройками браузера), другое принимает запись и ничего не хранит; настоящий `localStorage` jsdom так не умеет (его настоящую квоту проверяет тест, который пишет до ошибки переполнения). Сервера по адресу страницы в vitest нет, поэтому запрос сохранения идёт настоящим клиентом и настоящим `fetch` и падает так же, как без сети (`ApiError(0, 'network')`): это путь «связи нет»; ответы `200`, `401`, `409` и настоящий обрыв связи (`setOffline`) проверяет `e2e/session.spec.ts`. Число отправленных запросов тесты считают по состоянию стора (`tests/saves.ts`), а не обёрткой над `fetch`. Так же с занятым сервером (`429 rate_limited` и `Retry-After`) и с отказами сервера, которые страница говорит своими словами: «ответ сервера» в vitest не рисуется руками (самодельный HTTP-сервер, повторяющий формат ответа, разошёлся бы с настоящим, а настоящий шлюз тяжёлых запросов — в Rust). В vitest остаются чистые части (`busyRetryMs`, `serverRefusal`, ключи переводов против кодов в исходниках Rust), а поведение редактора проверяют `e2e/busy.spec.ts` (шлюз занят настоящим долгим расчётом — редактор показывает «считается», ждёт `Retry-After` и получает вердикт) и `e2e/refusals.spec.ts` (настоящие отказы сервера на русском и английском).
* Подводные камни интерфейса: глобальные классы `.row`, `.field`, `.empty`, `.kbd` из `styles/` перебивают одноимённые классы
  компонента (называйте свои иначе); клик по карточке должен доходить до обёртки Vue Flow — иначе Shift+клик не добавит узел в выделение
  (`ArchNode.vue`); в `content-visibility: auto` у карточек за экраном нет `innerText` (в тестах — `textContent`).
  Слои «стопки» экземпляров — `box-shadow`, а не дочерние элементы с отрицательным `z-index`: анимация входа делает карточку контекстом наложения, и слои легли бы поверх её фона. Закрытие окна по клику снаружи слушает `mousedown` на стадии захвата: холст останавливает мышиные события своей области (масштабирование d3-zoom), до всплытия они не доходят. Значки видов — имена из `src/lib/icons.ts` (реестр векторных компонентов; список в [CATALOG.md](CATALOG.md)): новый значок — строка в реестре и в импорте.

## Документация живёт вместе с кодом

* Таблицы правил, настроек, каталога продуктов и таблиц выпусков генерируются: `python3 deploy/gen-docs.py` (в CI — `--check`).
* Каталог по умолчанию (`catalog.json`, названия таблиц в `versions.json`, недостающие шаблоны IaC) собирается из исходников `deploy/catalog/` — `python3 deploy/catalog/build.py` (в CI — `--check`); пока пишете модуль продуктов, его проверяет `python3 deploy/catalog/lint.py <модуль>` (те же проверки без записи, [README каталога](../deploy/catalog/README.md)).
  Правите продукт — правьте исходник, не `catalog.json`: [README каталога](../deploy/catalog/README.md).
* Лицензии: проект — Apache-2.0 (`LICENSE`, `NOTICE`); список всего, что входит в сборку и на каких условиях, — `THIRD_PARTY_LICENSES.md`, его пишет `python3 deploy/licenses.py` из `Cargo.lock`
  и `package-lock.json`. В CI — `--check`: падает, если файл устарел или у зависимости лицензия вне списка принятых (`deploy/licenses.json`; копилефт туда не попадает). Добавили или убрали зависимость, или у неё сменилась лицензия, — перегенерируйте файл; обновление версии его не меняет (в списке нет версий, они в lock-файлах; `--versions` печатает их).
* Зависимости на уязвимости проверяет `cargo deny` (`backend/deny.toml`; `.github/workflows/security.yml` — то же в CI, каждый день и перед публикацией образа): `cargo install --locked cargo-deny@0.20.2`, затем
  `cargo deny --manifest-path backend/Cargo.toml --config backend/deny.toml --locked check advisories bans sources` (первый запуск скачивает базу RustSec); в `frontend` — `npm audit --omit=dev --audit-level=high`. Игнор уязвимости — запись с причиной и `review-by ГГГГ-ММ-ДД`, её срок проверяет `python3 deploy/check-deny.py`.
  Скрипты в `deploy/`, которые что-то решают, имеют тесты со своим провальным случаем: `python3 -m unittest discover -s deploy/tests` (нужны PyYAML и jsonschema: `pip install -r deploy/requirements-ci.txt`; `check-k8s-exposure.py` читает манифесты Kubernetes и портит настоящие, чтобы проверить, что он это замечает; проверки workflow и скрипты CI тестируются на настоящих временных репозиториях git и на настоящем выводе Playwright, без подделок). Правила разбора находки — [SECURITY.md](../SECURITY.md).
* Эталонные архитектуры собираются из `deploy/templates/` — `python3 deploy/templates/build.py` (в CI — `--check`); таблица в `docs/TEMPLATES.md` и цифры в `README.md` и `README.en.md` генерируются тем же `gen-docs.py`.
* Логотип и баннеры (`docs/images/logo.svg`, `banner.svg`, `banner.ru.svg`) рисует `python3 deploy/brand/build.py` (нужны `pip install fonttools brotli` и шрифты интерфейса из `frontend/node_modules`): текст в них —
  контуры, потому что SVG в README не может загрузить шрифт. Скриншоты README и карточку для ссылок на репозиторий (`social.png`: её загружают вручную в Settings → Social preview) снимает `deploy/brand/shots.mjs` с запущенного стека, на котором есть демо-проект
  `shop-prod` и включён ИИ (`cd frontend && E2E_EMAIL=… E2E_PASSWORD=… node ../deploy/brand/shots.mjs [имя …]`; кадр `ai` — настоящий ответ модели, поэтому снимается только по имени).
* Меняете API — правьте `docs/API.md` в том же коммите (каждый код ошибки — строка таблицы «Errors»: тест `every_error_code_is_documented` читает исходники сервера и падает на коде без строки; обработчики берут `Json`, `Path` и `Query` из `crate::json`, а не из `axum`: иначе запрос, который нельзя прочитать, получит текст вместо JSON); меняете поведение симулятора/правил — `SIMULATION.md` / `RULES.md`.
* Новое архитектурное решение — короткий ADR в `docs/adr`.

## Как добавить…

**Компонент (вид, продукт)** — без кода: Администрирование → Каталог → «Новый элемент» (`catalog.kind`): функция, поведение, признаки (`traits`),
роли, свойства, варианты (`variants`), таблица версий (`versions`). Чтобы он попал во встроенные значения — добавьте его в исходник `deploy/catalog/part_*.py` и выполните
`python3 deploy/catalog/build.py` ([CATALOG.md](CATALOG.md)).

**Вариант развёртывания** (топология HA, управляемый сервис) — запись в `variants` вида: `behavior`, `addTraits` (`managed`, `self-quorum`, `platform-quorum`), `defaults`, `roles`, `cost`, `versions`.
Тест `crates/engine/tests/products.rs` проверяет, что кворум и размещение учитывают вариант; тест размещения прогоняет каждый продукт и вариант на 1, 2, 3, 5 и 10 площадках.

**Версии продукта** — таблица выпусков (`catalog.versions`, `id` = `versions` вида): Администрирование → Каталог → Версии продуктов, либо `python3 deploy/versions-sync.py --add id=продукт-на-endoflife.date --name id="Название"`
(без аргументов обновляет все таблицы в `versions.json`; `--check` падает, если таблица старше `--max-stale-days`). Раз в неделю то же делает задача CI «Release tables»
(`.github/workflows/versions.yml`): обновляет таблицы, пересобирает каталог и документацию, записывает заново выводы движка для тестов фронтенда (`deploy/rerecord-fixtures.sh`), гоняет тесты и коммитит в `main`.
Тесты не должны зависеть от того, *когда* обновили таблицы: ожидаемую «рекомендуемую линию» берут из таблицы или из записанного отчёта, а не пишут числом.

**Схему размещения, платформу, параметры генератора** — без кода: Администрирование → Размещение ([PLACEMENT.md](PLACEMENT.md)); встроенные — `backend/crates/engine/defaults/placement.json`.

**Правило** — без кода, если подходит один из типов проверок ([RULES.md](RULES.md)): `rules.json` или админ-панель; поля `check`,
`params`, `severity`, тексты на каждом языке и `fixLabels`. Для нового *типа* проверки: вариант в `CheckType`, реализация в `checks.rs`,
тест на эталонной архитектуре в `crates/engine/tests/engine.rs`.

**Эталонную архитектуру** — файл `backend/crates/engine/defaults/templates/<id>.json` (в сборку он попадает сам, перечислять его нигде не нужно) или админ-панель; бо́льшая часть поставляемых пишется кодом в
`deploy/templates/` и собирается `python3 deploy/templates/build.py` ([TEMPLATES.md](TEMPLATES.md)). Шаблон не должен нарушать собственные правила и обещать больше, чем держит, — это проверяют тесты, `infra-architect check`
и `make iac-check`; у шаблона должны быть теги, значок, порядок, название и описание на двух языках (галерея в «Новом проекте» ищет по ним).

**Настройку** — запись в `crates/server/defaults/settings.json` (ключ, группа, тип, значение по умолчанию, подписи); чтение —
`cfg.settings.str|num|boolean|list(...)`. Форма в админ-панели и таблица в документации появятся сами.

**Язык интерфейса** — словари `src/i18n/<lang>.ts` и `<lang>.admin.ts`, регистрация в `i18n/index.ts`, язык в настройке `app.languages`;
тексты из конфигурации (`LText`) заполняются на новом языке в админ-панели.

## Проверка в браузере

Playwright (Chromium) используется для сквозных проверок интерфейса против запущенного стека (`frontend/e2e`):

```bash
cd frontend && E2E_BASE=http://localhost:8080 E2E_EMAIL=admin@example.com E2E_PASSWORD='…' npx playwright test
```

Наборы: `editor` (редактирование, версии, конфликты, дрейф), `admin` (в том числе правка схемы размещения → мастер → сброс), `export` (отчёт IaC «сгенерировано / не сгенерировано», закрытие
пробела через «Заполнить», SVG-файл), `ux` (что заполнить для «нет данных», цели и план ёмкости, палитра команд, выделение нескольких
узлов, семантический зум, миниатюры и копирование проектов), `placement` (мастер размещения: от одного ЦОД со стойками до десяти площадок, сравнение, создание проекта), `product`
(продукты и варианты в библиотеке и инспекторе, версия и срок её поддержки), `motion` (режимы анимации и их скорость), `playback` (воспроизведение отказа по шагам), `tour` (обучающий тур),
`polish` («Отменить» после удаления, пустое состояние, скелетоны), `canvas` (схема вписывается в холст, не прячась за плавающими панелями; вид пользователя не трогают),
`header` (шапка редактора помещается в окно любой ширины от 1280 до 2560 px: ничего не налезает друг на друга и не уходит за край, имя проекта читается), `a11y` (доступность: **axe-core** на основных экранах — у каждого поля есть подпись, у страницы заголовки и ориентиры, текст держит контраст WCAG AA; версия axe зафиксирована, CSP страницы
снимается только в этом наборе, чтобы передать axe скрипт; в том числе большая схема, отдалённая до уровней «компактно» и «сводка», с отказом на экране и без: имя карточки содержит написанное на ней, WCAG 2.5.3), `keyboard` (схема руками без мыши: одна остановка Tab на всю схему вместо 62, стрелки между карточками и вид следует за фокусом, Enter / Shift+Enter / Delete делают то же, что щелчок, связи — через палитру и инспектор, имя у каждой карточки, таблица горячих клавиш — диспетчер, в том числе на русской раскладке, пропускные ссылки, библиотека как один элемент списка, озвучивание вердикта после правки), `tabs` (каждый список вкладок — шаблон ARIA «Tabs»: стрелки, Home и End двигают фокус и выбор, у выбранной вкладки `aria-controls` ведёт на `tabpanel`, который назван ею), `dialog-focus` (каждое окно — новый проект, переименование, удаление, экспорт, версии, матрица отказов, оценка, горячие клавиши, мастер размещения, «О программе», палитра — берёт клавиатуру, держит её (сорок Tab и сорок Shift+Tab не выходят и обходят ровно его элементы), блокирует страницу за собой (`inert`) и возвращает фокус тому, что его открыло; окно над окном, палитра над окном, сообщение над окном, меню), `navigation` (карточка проекта — настоящая ссылка: Tab, Enter, Ctrl+клик, кнопки карточки над ней; заголовок вкладки у каждой страницы, в том числе у двадцати страниц админки, он следует за переименованием проекта и языком; после перехода фокус на заголовке новой страницы (у проекта, который пришёл с опозданием, — тоже на заголовке с его именем, а не на области `main`), а не при смене запроса адреса и не при переходе между разделами админки), `ai-off` (стенд без ключа ИИ: нет строки запроса, переключателя «ИИ / вручную», вкладки чата и их команд палитры, нет запроса истории чата; холст начинается сразу под шапкой; текст пустой схемы не зовёт к ИИ и называет библиотеку, только пока она открыта; одна подсказка у администратора, её можно скрыть; тур обходит отсутствующий шаг. Пропускается на стенде с ключом — там то же самое проверяет `tests/aiChrome.test.ts` на настоящих хранилищах). В среде без загружаемых браузеров укажите свой Chromium: `PW_CHROMIUM=/путь/к/chrome`.

## CI

Рабочие процессы — `.github/workflows/` (`ci.yml`, `security.yml`, `versions.yml`), общие шаги — составные действия `.github/actions/` (`rust-toolchain`, `python-tools`).

```
scope ──┬─ backend, msrv, frontend, iac, manifests, security    независимы друг от друга и стартуют сразу
        └─ build ──┬─ image-checks     собранный образ так, как его запускает пользователь: smoke, шлюз `check`, Trivy по пакетам ОС
                   └─ e2e (4 части) ── e2e-report     браузерные тесты; общий отчёт; все ли тесты, что есть, прошли
docs                                   дешёвые проверки всего сгенерированного и самих workflow; идёт всегда
ci-ok                                  единый вердикт
publish                                только `main`, после `ci-ok`: выкладывает тот же образ, что проверяли
```

* **Образ собирается один раз** (`build`, слои из кэша GitHub) и передаётся артефактом (`image.tar`, хранится сутки): `image-checks`, каждая часть `e2e` и `publish` берут его, а не собирают заново. Раньше `image` ждал `iac` (минуты, образу он не нужен), а `publish` собирал образ второй раз.
  Образ в `publish` — тот, что прошёл проверки (`docker load`, `docker tag`, `docker push`); отдельной аттестации сборки (provenance), которую добавляла сборка прямо при выкладке, у него нет — это за релизным процессом.
* **`ci-ok` — единственная проверка, которую нужно сделать обязательной**: Settings → Branches → Branch protection rule для `main` → Require status checks → `ci-ok` (из кода это не включить). Она ждёт все остальные задания (`deploy/check-workflows.py` проваливает `docs`, если новое задание в её список не попало) и судит их результаты (`deploy/ci-ok.py`): `failure` и `cancelled` — красное; `skipped` допустимо только когда `scope` решил, что изменилась одна документация. Обязательное задание, пропущенное из-за упавшего соседа, GitHub считает пройденным — поэтому требовать нужно `ci-ok`, а не отдельные задания.
* **Одна документация не запускает тяжёлое.** `scope` (`deploy/ci-scope.py`) смотрит, какие файлы изменил pull request; если **каждый** из них — документация, `backend`, `msrv`, `frontend`, `iac`, `manifests`, `security`, `build`, `image-checks` и `e2e` пропускаются (идут только `docs` и `ci-ok`, порядка двух минут). Документация — короткий и узкий список: `docs/**`, `*.md` в корне, шаблоны issue/PR, `CODEOWNERS`, `dependabot.yml`. Остальное — код, в том числе то, что попадает в образ (`THIRD_PARTY_LICENSES.md`, `LICENSE`, `NOTICE`, `frontend/README.md`), `docs/API.md` (его читают два теста сервера: тест `deploy/tests/test_ci_scope.py` ищет в исходниках тестов другие страницы `docs/`, которые они читают), сами workflow и всё неизвестное. Пуш в `main` и ручной запуск не пропускают ничего. Ошибка в скрипте, пустой список файлов, недоступная база — тоже «всё запускать».
* **Параллельность.** Один pull request — одна группа: новый пуш отменяет предыдущий запуск. Пуш в `main` ничего не отменяет (каждый коммит `main` проверяется и может быть выложен) и встаёт в очередь за предыдущим, чтобы `publish` не положил старый коммит поверх нового.
* **Браузерные тесты идут частями.** Playwright режет набор на столько частей, сколько записей в матрице `shard` (`--shard=i/n`, `n` — размер матрицы, `strategy.job-total`); у каждой части свой раннер и **свой стек** (тесты администрирования меняют настройки всей установки, делить стек нельзя). Чтобы добавить часть, допишите число в `shard`. Playwright делит по числу тестов, не по времени, так что части не равны: смотрите самую долгую (`e2e-report` и журнал) и добавляйте часть, когда она длиннее сборки образа. `e2e-report` склеивает отчёты частей (`merge-reports`), выкладывает HTML-отчёт (7 дней) и сравнивает с `playwright test --list`: если какой-то тест не выполнился (часть упала, не записав отчёт), выполнился дважды или пропущен (`test.skip`), задание красное (`deploy/check-e2e-report.py`). Упавшая часть оставляет скриншоты и журнал стека на 7 дней. Файл `frontend/playwright.config.ts` для этого не менялся: `--shard` и `--reporter=list,blob` — аргументы командной строки.
* **Проверка IaC**: чарты Helm скачиваются **один раз** в `$IAC_CACHE/charts` и рендерятся из файла (`helm template --repo …` на каждый вызов заново скачивает и разбирает индекс репозитория, 6 МБ у prometheus-community, — на этом уходило три четверти времени), схемы `kubeconform` и провайдеры Terraform тоже кэшируются, примеры проверяются в параллель (`IAC_JOBS`, 4 по умолчанию). В CI каталог кэша восстанавливается `actions/cache` по ключу из `engine.json`, `defaults/iac/*.json` и `deploy/iac-check/**`; `make iac-check` держит его в томе `iac-cache`. Чарты, которые больше не закреплены, из кэша удаляются.
* **Компилятор Rust** — тот, которым собирается образ: `ARG RUST_VERSION` в `Dockerfile` (действие `rust-toolchain` читает его и ставит `rustup toolchain install`). Файла `rust-toolchain.toml` в `backend/` нет и быть не должно: rustup 1.28 не устанавливает названный в нём компилятор, а отказывает, и `docs` (cargo metadata), сборка образа и `docker-compose.test.yml` ломаются везде, где есть только `stable`. Задание `msrv` собирает всё (`cargo check --workspace --all-targets --locked`) самым старым компилятором, который обещает `rust-version` в `backend/Cargo.toml` (1.89); если оно покраснело — правят код или поднимают обещание (там и в «Rust 1.89+» этого файла и `CONTRIBUTING.md`).
* **Права и закрепление.** Токен по умолчанию — `contents: read`; писать может только `publish` (`packages: write`) и задание `commit` в `versions.yml` (`contents: write`, оно запускает один скрипт и git). Каждое стороннее действие закреплено коммитом с версией в комментарии, у каждого задания есть `timeout-minutes`, у каждого `checkout` — `persist-credentials: false` (кроме того, что делает `git push`), `pip install` — только с `-r <файл>` или `==`. Это не договорённость, а проверка в `docs`: `python3 deploy/check-workflows.py` (правила), `python3 deploy/pin-actions.py --check` (закрепление; без `--check` закрепляет новые `uses: owner/repo@v1` коммитом, `--verify` сверяет коммиты с тегами в комментариях по сети), `actionlint` (разбор workflow и `shellcheck` по скриптам). Новое действие: напишите `uses: owner/repo@v1`, выполните `python3 deploy/pin-actions.py` и закоммитьте. Версия `actionlint` и контрольная сумма записаны в `ci.yml`; новую берут вместе с суммой со страницы релиза.
* **Пакеты Python проверок** (`deploy/requirements-ci.txt`: PyYAML и jsonschema) закреплены версиями **и хешами** и ставятся в виртуальное окружение (действие `python-tools`, `--require-hashes` отказывает файлу без хешей); PyYAML внутри образа проверки IaC — тоже (`deploy/iac-check/requirements.txt`). Локально: `pip install --require-hashes -r deploy/requirements-ci.txt`.
* **«Таблицы выпусков»** (`versions.yml`, раз в неделю): задание `refresh` только читает (`contents: read`) — скачивает сроки, пересобирает, гоняет тесты (cargo и npm исполняют чужой код) и передаёт патч с теми файлами, которые обновление вправе менять; задание `commit` вправе писать, не запускает ни cargo, ни npm и **отказывается** применять патч, который трогает что-то ещё, переименовывает, удаляет или делает ссылкой (`deploy/release-patch.py`; список разрешённого там же: новый файл, который обновление начнёт писать, добавляют туда). Коммит токеном workflow не запускает CI: за него отвечают тесты `refresh`.
* **Dependabot** следит за всем, что можно: Cargo, npm, workflow и составные действия, оба `Dockerfile`, файлы compose, Python проверок (`deploy/check-dependabot.py` в `docs` проваливается, если появился каталог с lock-файлом, `Dockerfile`, compose-файлом, `requirements*.txt` или workflow без записи в `.github/dependabot.yml`). Релиз предлагается не раньше чем через 5 дней после выхода (14 для major в Cargo и npm: `cooldown`). Образы, названные переменной (`FROM ${REGISTRY}/node:${NODE_VERSION}-…`, `${REGISTRY:-docker.io/library}/postgres:16-alpine`), Dependabot, скорее всего, не видит: запись есть, а pull request'ов по ним не будет — смотрите Insights → Dependency graph → Dependabot.

Локально то же, что в `docs`: `python3 deploy/check-workflows.py && python3 deploy/pin-actions.py --check && python3 deploy/check-dependabot.py && python3 -m unittest discover -s deploy/tests`.
